Aside: Python Magic Methods

Python Magic Methods

Remember: Any piece of data in Python is an object that belongs to a class.

You will often see references to methods with two underscore characters before and after the name; for example, __init__(), __str__(), __len()__.

  • Called dunder (short for double underscore) or magic methods.
  • Do not make up your own method names with the double underscore notation.
  • You can definitely implement these methods for your own classes.

You will run into these methods in the Python documentation.

You can write other methods with dunder names, but you will just confuse everybody.

By using dataclasses, you get reasonable implementations of several of these methods for free; for example, __init__() and __str__().

Example Magic Methods

Magic methods are used by Python to implement internal behaviours and operator overloading.

  • When you call print(x), Python displays the result of x.__str__().
  • When you call len(x), Python returns the result of x.__len__().
  • When you write x + y, Python will call x.__add__(y).
  • When you write x[i], Python will call x.__getitem__(i).
  • When you write x[i] = y, Python will call x.__setitem__(i, y).
  • …

Most Python operators are just syntactic sugar for method calls; in other words, a way of writing method calls which is easier for humans to read.

Aside: Class Hierarchies and Interfaces

Class Hierarchies

Remember: Any piece of data in Python is an object that belongs to a class.

When we have a bunch of related classes, we often organize them in a hierarchy.

  • Classes have a parent or superclass from which they inherit attributes and methods.
    • If a class definition does not list a superclass, then it inherits from Python’s object class.
  • Classes can have children or subclasses which implement (or even change) their methods and attributes.

Do you need to know how to build or even use class hierarchies for the exam? No.

It is useful to know this vocabulary when reading Python documentation / explanations, and also to understand interfaces.

Why Class Hierarchies?

Conceptually, the idea is that you can work with an object as if it was an instance of the parent class rather than needing to know to which specific child class it belongs.

In particular, different children might:

  • Store their data in different ways.
  • Store different data.
  • Implement the same method in different ways.

But the user only needs to know the common method’s signature (typically given in the parent class).

Formal hierarchies are important in strongly typed languages, such as C++ or Java. In those languages the type of every object must be known in advance, so the ability to pretend to be a parent type is powerful.

Python uses informal “duck typing” (if it walks like a duck and quacks like a duck, it is a duck), so you don’t need to formally be an object of a child class in order for this trick to work.

Interfaces

A contract specifying which method(s) a child class should implement.

  • An interface is not a class.
  • It provides only the signature(s) of the required method(s), not implementation(s).
  • You cannot create an object instantiating an interface.

You can create classes which inherit from / implement an interface.

  • Make sure that the class implements the required method(s).
  • When you instantiate an object, it will implement the interface.

Often we would like a group of different objects to implement the same methods, but we don’t want to have a full parent class.

In Python the distinction is mostly for human design purposes: We use “interfaces” for relatively light-weight contracts without common data representations, and “superclasses” for more complex data representations.

Python also has an intermediate category, abstract base classes, which cannot be instantiated but which can contain attributes and method implementations.

Do you need to know how to build interfaces for the exam? No

It is useful to know this vocabulary when reading Python documentation / explanations. In particular, I do want you to understand what I mean when I mention iterable or hashable objects.

Useful Interface: iterable

  • Intuition: If you can write a for loop over the elements of the object.
  • Contract: Object implements the __iter__(self) method.
  • Practical effects:
    • You can write loops: for item in x: ...
    • You can write list comprehensions.
    • You can trivially convert to a list: list(x) or tuple(x).

We will not expect you to implement classes which have the iterable interface.

I want you to be able to understand what I mean when I say “any iterable / hashable object”, rather than always having to say “list” / “immutable object” and feel uncomfortable about it.

Examples of iterable

Examples:

  • list, tuple, str. Elements will always come out in the same order in which they were created.
  • set. Elements may come out in a different order.
  • dict. The iteration is over the keys, and elements may come out in a different order.
  • The objects returned by range() and enumerate().
  • Files, pandas Series and DataFrames, and many more.

When you write a loop over an iterable object, you can think of it as a list. But behind the scenes Python does not create a list but rather works with the data in its existing representation.

In particular, range(n) doesn’t need memory proportional to \(n\); instead, it just keeps track of the current element, how to get to the next element, and when to stop. If you type list(range(n)), then you will create a list and use memory proportional to \(n\).

Useful Interface: hashable

  • Intuition: An object that is immutable.
  • Contract: Object implements the __hash__(self) and __eq__(self, other) methods.
  • Technical details: A magic number (the hash value) with a constant number of digits can be computed from the object such that:
    • You will always get the same number for this object.
    • You will (almost) always get a different number for any other object.
  • Practical effects:
    • The object can be used as a key in a dictionary or added to a set.
    • The programmer need not worry about aliasing or function side-effects.

There are objects which are immutable but not hashable and vice versa, but the former are rare and the latter are rare and almost always a bad idea, so we’ll ignore the distinction.

The size (storage requirement) of a hash value is constant no matter how much data is in the corresponding object.

The way that dictionaries / sets can look things up so fast is because they use the hash value like an index.

It is okay if you very occasionally get the same number from two different objects. This is called a hash collision, and you can check for it with a subsequent call to __eq__(). More important is that objects whose data is similar should produce very different hash values. That means computing the hash value may be expensive for a large object (such as a long tuple).

As a side note: The hash value only needs to stay constant during a single run of the program. Python may produce different hash values on different runs.

Aliasing and side-effects are an issue because the data in an object can change without an explicit reference to the object. But immutable objects cannot change, so the problem disappears.

Examples of hashable

  • All the simple atomic types: int, str, bool, float, NoneType.
  • NamedTuples (but not dataclasses).
  • Many basic mutable types have an immutable version.
    • For example: tuple, frozenset, (as of Python 3.15) frozendict.
  • The union of other immutable types.
    • For example, optional type: some_type | None.
